# 检索 Golden Set（起点版）

> 用途：比较「精确事实车道」与「跨章关联车道」的检索质量，决定是否值得上 1 跳深召回。
> 语料：本机小说 `22b30e6861e5`（《恋爱吧！折花君》）当前索引。
> 说明：这是 **起点版**，gold chunk 由当前实体/关系/情节线文档生成；上线前请人工复核 10 条。

## 指标

| 指标 | 说明 |
|---|---|
| R@5 / R@10 | gold chunk 是否进入前 5/10 |
| MRR | 第一个 gold chunk 的排名倒数 |
| Precision@5 | 人工评“这条结果对写作有用”的比例 |
| p95 latency | 交互路径 ≤5s；后台 ≤10s |
| 护栏 | 直接事实类 R@5 不得比当前基线下降 >2 个点 |

## 对比组

1. `dense`：`DenseTopK=20, LexicalTopK=0`
2. `hybrid`：`DenseTopK=20, LexicalTopK=20`
3. `hybrid+lexical`：上面的词法层（jieba 预分词 + OR）
4. 仅在 3 仍不足时，再测 1 跳深召回

## 本机可复现性说明（2026-10）

原 40 条查询指向 `22b30e6861e5`（《恋爱吧！折花君》）的实体库索引，本机 `~/.mythology/vectors.db`
里是另一部小说（`2c2410d54e08`，76 块）的索引，gold chunk id 全部不存在。实测 40 条里只有 5 条能在当前语料上评估，
且两臂都排第 1 —— **无区分度**。

因此把评测固化成一条命令（`src/RetrievalEval` 命令行 + `src/StabilityHarness/Retrieval` 评测库），gold 从**库本身**推导，不依赖外部标注：

```bash
dotnet build src/StabilityHarness -c Release
cp ~/.mythology/vectors.db /tmp/v.db     # 评测只读打开，但建议用副本
./src/StabilityHarness/bin/Release/net10.0/StabilityHarness \
  retrieval-eval --db /tmp/v.db --novel 2c2410d54e08 --gold strict --verbose
```

gold 规则：
- 档案文档正文以 `角色: ` / `地点: ` / `情节线: ` / `场景: ` / `组织: ` / `道具: ` 开头 → 由此拿到实体名与其档案文档；
- **Fact**（`{名}的性格和设定是什么？`）：Strict = 该档案文档；Loose = 所有提到该名的文档；
- **Partial**（名字前 2 字）：Loose gold = 提到该名的文档；
- **Relation**（`和{名}相关的关系是什么？`）：gold = 提到该名的关系陈述。

五个方案：
- **A 基线**：默认词典 + 最佳路径（`Cut`）；
- **B 现行**：实体名注册 + 索引侧 2/3 字片段；
- **C 二轮词项扩展**：首轮 BM25 挖词项 → 二轮 → 交错合并（SAG2 式，无 LLM）；
- **D 文档级 MMR**：按「相关度 − 与已选项最大相似度」贪心选取（同文档相似度 1.0，否则 token Jaccard），DPP 的便宜近似；
- **E 完美判定重排（oracle 上限）**：在 top-20 候选里把 gold 提到最前 —— 用来量化「如果 JEV/判定重排完全准确，能提升多少」。

实测（54 条查询，候选上限 100）：

| 口径 | 方案 | R@5 | R@10 | AE@5 | MRR |
|---|---|---|---|---|---|
| strict | A 基线 | 74% | 76% | 65% | 0.605 |
| strict | **B 现行** | **94%** | **98%** | **83%** | **0.778** |
| strict | C 二轮扩展 | 91% | 98% | 80% | 0.774 |
| strict | D 文档级 MMR | 94% | 98% | 83% | 0.778 |
| strict | **E 判定重排上限** | **98%** | 98% | **89%** | **0.981** |
| loose | A 基线 | 76% | 76% | 54% | 0.665 |
| loose | **B 现行** | **96%** | **98%** | **72%** | **0.835** |
| loose | C 二轮扩展 | 94% | 98% | 70% | 0.837 |
| loose | D 文档级 MMR | 96% | 98% | 72% | 0.835 |
| loose | **E 判定重排上限** | **98%** | 98% | **78%** | **0.981** |

读法：
- **B 相对 A**：R@5 从 ~75% 提到 ~95%、AE@5 从 ~60% 提到 ~80%，是这次改动的本体收益。
- **C 没有收益**：单小说小语料首轮已覆盖证据，二轮扩展只带噪声（SAG2 的收益来自多跳 & 大语料），不接入产品链路。
- **D 中性**：本语料 76 块 / 69 篇文档 ≈ 一块一篇，MMR 无「同源冗余」可去；长篇小说（12 块/章）才可能有效，且已有 `MaxPerChapter` 粗粒度约束。
- **E 说明「排序」是剩余损失所在**：完美重排能把 MRR 从 0.778 拉到 0.981、AE@5 83% → 89%。
  这正是 `JudgeRerank`（SystemOne `noul` 判定，等价 SAG2 的 JEV）在做的事——**它已实现且可在设置页开启**，
  默认关；本仓没有 SystemOne 端点，所以只测了上限。

### 真 JEV 实测（`10.1.44.46:8009`，llama.cpp `/v1/systemone`，`d1-omni-600M`）

命令：`retrieval-eval --db /tmp/v.db --novel 2c2410d54e08 --gold strict --jev-url http://10.1.44.46:8009`
（配置取 LKK `appsettings.json` 的 `AttachmentServices.Jev`：`ApiKey=local`、`TimeoutSeconds=15`、`MaxStateChars=1200`）

| 方案 | R@5 | R@10 | AE@5 | MRR | 54 条耗时 |
|---|---|---|---|---|---|
| B 现行 | 94% | 98% | 83% | 0.778 | <1 s |
| **F 真 JEV 重排** | **94%** | 98% | **83%** | **0.779** | **3 min 21 s** |

逐段概率诊断（`MaxStateChars=1200` / 12 候选 / 截断 92 字）：

```
「陈折花的性格是什么？」
  ★gold p=0.851 score=1.351  关系: 陈折花 与 汐見 美海
  ★gold p=0.843 score=0.671  角色: 陈折花 性别男 年龄16 定位P…
  ★gold p=0.208 / 0.549 / 0.175 / 0.487（其余关系/正文，分数被压下）
「潮音堂书店在哪？」
  p=0.769 / 0.752 / 0.894 … 地点: 潮音堂书店（判定基本饱和）
```

结论：
- **能用**：端点、鉴权、`noul` 评分、分批、超时都跑通；
- **本语料没有收益**：F ≈ B（MRR 0.779 vs 0.778），但每条查询要 **2–9 s**，54 条 3 分 21 秒；
- 判定本身有区分度（同一次请求内 0.17~0.89），但它把「关系陈述」判得和「角色档案」一样相关（0.85 vs 0.84），
  而我们 strict gold 只认档案文档——**判定标准与 gold 定义不一致**，所以排序不改善；
- 加大 `MaxStateChars`（4000 / 8 候选 / 444 字）反而更慢（9.2 s/条）且没有更好。

因此：JEV 保持**可选、默认关**。它真正可能回本的地方是「没有 embedding 模型（dense 是 Dummy）」
或「语料大、词法候选噪声多」的场景——那需要用真实库再跑同一条命令对比。

### 全臂实测（真实 embedding `10.1.44.242` + 真实 JEV `10.1.44.46:8009`）

命令：

```bash
dotnet run --project src/RetrievalEval -c Release -- retrieval-eval \
  --db /tmp/v.db --novel 2c2410d54e08 --gold strict \
  --emb-url http://10.1.44.242 --emb-key <key> \
  --jev-url http://10.1.44.46:8009 --jev-key local --jev-candidates 6 --jev-maxstate 800
```

| 臂 | R@5 | R@10 | AE@5 | MRR | 54 条耗时 |
|---|---|---|---|---|---|
| A 基线（默认词典·`Cut`） | 74% | 76% | 65% | 0.605 | <1 s |
| **B 现行**（实体注册 + 2/3 字片段） | **94%** | **98%** | **83%** | 0.778 | <1 s |
| C 二轮词项扩展（SAG2 式） | 91% | 98% | 80% | 0.774 | <1 s |
| D 文档级 MMR | 94% | 98% | 83% | 0.778 | <1 s |
| E 完美重排（oracle 上限） | **98%** | 98% | **89%** | **0.981** | <1 s |
| F B + 真实 JEV（12 候选 / 1200 字） | 94% | 98% | 83% | 0.778 | **3 min 21 s** |
| G 纯 dense（wemm-embedding 1024 维） | 61% | 72% | 50% | 0.548 | ~5 s（含建向量） |
| H 混合 RRF（B + G） | 93% | 96% | 80% | **0.803** | <1 s + 建向量 |
| I 混合 + 真实 JEV（6 候选 / 800 字） | 91% | 96% | 78% | 0.802 | **4 min 09 s** |

读法：
- **G 纯 dense 明显弱于词法**（61% vs 94%）：本评测的 gold 是“实体档案”，正是词典+片段发射负责的场景——
  这也解释了为什么这次词典/发射规则的改动收益这么大。dense 的价值在**互补**：H 的 MRR 最高（0.803）。
- **JEV 在本语料是净负**：F/I 都没提升（I 甚至因重排把 5 条挤出前 5 而下降），而每条查询要 2~9 s；
  把候选从 12 降到 6、state 从 1200 降到 800 **并没有变快**（端点单请求延迟主导），说明瓶颈不在 payload 大小。
- 判定口径是根因：`JudgeRerank` 的 yes 判据是「该段落含有与检索意图直接相关的具体内容（部分相关也算）」，
  于是「陈折花 与 美海 的关系」被判 0.851，而真正的「角色: 陈折花 档案」只有 0.843 ——
  它和 strict gold（只认档案）**本来就不是同一个问题**。想让它回本，要改的是判据/提示词，不是加大候选。

### 判据改造实测（`--jev-criteria answers`）+ 一个评测 bug 修正

发现并修正了评测本身的一处失真：F/I 臂给候选的分数原本用 `1/(i+1)`（得分差距极大），
导致 `JudgeRerank` 的乘性调节**永远翻不动顺序**（这也是上一轮 F≈B 的假象）。
改成与产品一致的 RRF 量级 `1/(60+rank)` 后重测：

| 口径 | 判据 | R@5 | AE@5 | MRR | 耗时 |
|---|---|---|---|---|---|
| strict | 无重排（B） | 94% | 83% | 0.778 | <1 s |
| strict | `relevant`（旧判据） | 80% | 67% | 0.629 | ~2 min |
| strict | **`answers`（新判据）** | **91%** | **76%** | 0.630 | ~2 min |
| strict | oracle 上限 | 98% | 89% | 0.981 | <1 s |
| loose | 无重排（B） | 96% | 72% | 0.835 | <1 s |
| loose | `relevant` | 81% | 52% | 0.695 | ~2 min |
| loose | **`answers`** | **93%** | **61%** | 0.686 | ~2 min |

结论：
1. **`answers` 判据明显优于旧判据**（strict R@5 +11pp / AE@5 +9pp；loose +12pp / +9pp），已设为默认
   （`SystemOneRerankConfig.Criteria = "answers"`），并由 `JudgeRerank.CriteriaFor(profile)` 按档位回落：
   `ConsistencyCheck` → answers，其余（写作上下文/伏笔联想/偏好）→ relevant。
2. **但这个 600M 判定模型整体仍不如不重排**（strict 91% vs 94%、AE@5 76% vs 83%），
   且每条 2 s 量级。oracle 上限是 98%/89%/0.981 —— 差距全在判定质量。
   因此 JEV 保持**默认关**；要回本需要更强的判定模型，或只在“没有 embedding 模型”的库上启用。

正确性修正：早期版本把「全程命中」当成 AE@k，虚高到 98%；现已改为**前 k 条内命中数**，上表为修正后数值。

结论：B 相对 A 把 R@5 从 ~75% 提到 ~95%、AE@5 从 ~70% 提到 98%；
**C（SAG2 式二轮扩展）在本语料上没有收益**（单小说、首轮已覆盖证据），它是为多跳/大语料设计的，故不接入产品链路。

## 判定规则

- `fact` / `alias` / `relation` 走 **P 车道**：`ConsistencyCheck` 或 `WriteContext`，不做扩展。
- `association` 走 **A 车道**：`ForeshadowingSearch`，可测 1 跳深召回。
- `negative` 不设 gold；若 top1 分数接近正例 top1，说明检索阈值/噪声有问题。
- 深召回上线门槛：A 车道 R@5 相对 hybrid 提升 ≥10%，P 车道 R@5 不降，p95 ≤5s。
