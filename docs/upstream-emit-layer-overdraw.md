# 已撤回：此前的 overlay emit 归因未复现用户操作路径

本文件原先被写成可提交给 XenoAtom.Terminal.UI 的 issue 草案。该结论已撤回，**不要直接提交**。

## 新的截图与主题证据（2026-10-06）

用户提供的两张 `EntityEditDialog` 截图显示：

- 图 1：姓名、年龄输入框处于未聚焦状态，输入区域出现一条暗色填充。
- 图 2：点击姓名输入框后，姓名输入区域变白；年龄输入框仍保留未聚焦填充。

修复前，`ThemeRegistry.DesertLight.UiTheme` 使用 `Theme.DefaultLight`。运行时值：
`InputFill = RGBA(0,0,0,16)`，`InputFillFocused = RGB(255,255,255)`。

截图中的状态变化与此一致：未聚焦输入框使用半透明黑色填充，聚焦输入框使用白色填充。修复后，Desert Light
使用调色板对话框面色 `DialogContentBg`，并保留白色聚焦底。

## 先前证据的边界

旧终端录制摘要中确实记录了对话框矩形内两行各 60 个空格的写入；但该记录没有和用户现在描述的
hover / focus 序列逐步对齐，也没有识别出写入者的具体控件。旧测试只检查合成 `CellBuffer`，
并不能单独证明真实终端输出发生 overlay z-order 错误。因此不能据此断言这是框架 emit 缺陷。

OSC 11 应保持为应用主界面底色 `ConversationBg`，不应用对话框或输入控件颜色掩盖此类现象。
若本次输入填充修复后，鼠标悬停对话框边框或切换 tab 仍出现独立色块，再按用户实际事件序列重新
录制终端字节流并定位；在那之前没有可提交的上游问题结论。

## 第二轮复核：90×44 六态逐格转储（2026-10-06）

按用户实机形态（90×44、Desert Light、`EntityEditDialog` 打开、右侧面板有内容）对真实
`TerminalApp` 帧逐格转储，覆盖六个状态：初始 → 指针移出（右侧 / 左侧）→ 点击「姓名」输入框（聚焦）
→ 打开「性别」下拉 → 切到「性格描写」页。检查对话框右缘 2 列及邻近列（x=82..89）：

- 六个状态的「行宽（90/91）」与「右缘无背景格 / 对话框奶油底格」普查**全部为空**：
  右缘逐格均为主题底色 / 对话框边框色，无未绘制格、无纯黑 / 纯白格。
- 唯一非空内容均为预期视觉：右侧面板搜索框尾段与行菜单 `⋯`（主题色）、对话框右边框列、
  主分隔条设计字形 `▄` 的露出尾段（y=26，底色 = 面板色）。
- 结论：输入填充修复后，「对话框右缘黑 / 白块」在本机形态下不可复现。结构性守卫在案：
  `RealFrameBlackBlockTests`（真实帧未绘制格 / 纯黑格普查，含悬停与聚焦态）、
  `TerminalOutputFidelityTests`（发射字节 vs 帧缓冲逐格比对，覆盖悬停 / 聚焦 / 下拉序列）、
  `ScrollBarThemeLiveTests` 与滚轮用例（`WheelOverSceneList_*`）。一次性探针
  `RightEdgeProbeTests` 已删除，不入库。

实机若仍有约一个字符宽、随主题变色的残块：先看启动时 `TerminalWidthProbe` 的宽度探测日志
（终端把 CJK 画成 1 格宽、或把歧义字形画成 2 格宽都会被记录，可回传）；改用等宽 CJK 字体
（Sarasa Mono CJK / Noto Sans Mono CJK）可根治。
